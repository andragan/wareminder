## Context

WAReminder is a Chrome MV3 extension with a Supabase backend (PostgreSQL + edge functions) and Paddle for payments.

**Current state:**
- Extension still relies on Chrome Identity and Google OAuth tokens as its primary frontend credential
- `get-subscription-status` and `create-paddle-checkout` use different trust models today
- `user_profiles` is no longer linked to `auth.users` after migration 006
- `plan_type` exists in both `user_profiles` and `subscriptions` — redundant and drift-prone
- Plan enforcement (reminder limits) still happens largely in extension code
- Several subscription/auth flows remain stubs or hybrid placeholders

**New architectural direction:** move to Supabase Auth entirely for user-facing identity, sessions, and authorization while keeping Google as the upstream sign-in provider.

## Goals / Non-Goals

**Goals:**
- Make Supabase Auth the sole user-facing authentication and session authority
- Keep Google sign-in for users, but run it through Supabase Auth instead of custom token validation
- Restore `auth.users` as the canonical identity anchor for app data and subscriptions
- Make all user-facing backend calls authenticate with Supabase JWTs
- Move all plan enforcement to the backend (reminder limit checks)
- Eliminate data redundancy (`plan_type` only in `subscriptions`, not `user_profiles`)
- Replace hybrid auth recovery logic with a standard session restore / refresh model
- Keep the existing Paddle payment integration working

**Non-Goals:**
- Supporting the legacy Google-access-token backend contract indefinitely
- Changing the Paddle payment provider or adding new providers
- Redesigning the popup UI layout
- Implementing real-time subscription push (Supabase Realtime) — polling at 24h interval is sufficient
- Offline premium access

## Decisions

### 1. Supabase Auth SHALL own user identity and sessions

**Decision:** WAReminder will treat Supabase Auth as the sole source of truth for user identity and user sessions. Google remains the sign-in provider, but Supabase Auth issues and refreshes the JWTs used by the extension.

**Why?** This eliminates the custom token-validation layer in edge functions and restores a standard authentication boundary: user signs in, receives a Supabase session, and presents a Supabase JWT to user-facing backend endpoints.

**Alternative considered:** Continue validating Google access tokens directly in edge functions — rejected because it preserves a custom auth bridge and keeps user identity outside `auth.users`.

### 2. The Chrome extension SHALL use `launchWebAuthFlow` with a Supabase session-bearing redirect

**Decision:** The extension SHALL initiate Google sign-in through Supabase Auth, launch the login with `chrome.identity.launchWebAuthFlow(...)`, and use the Chrome redirect URL generated by `chrome.identity.getRedirectURL(...)`. The final redirect SHALL carry the Supabase session back to the extension so the extension can parse and store the session locally.

**Chosen flow:**
1. The extension generates `https://<app-id>.chromiumapp.org/...` with `chrome.identity.getRedirectURL(...)`
2. The extension starts Supabase Google OAuth with that redirect URL
3. The extension launches the returned URL with `chrome.identity.launchWebAuthFlow({ interactive: true, ... })`
4. Supabase redirects back to the Chrome extension redirect URL with a session-bearing result
5. The extension parses the returned URL, extracts the access and refresh tokens, and stores the Supabase session

**Why this flow?**
- It is Chrome-extension-native and works with `launchWebAuthFlow`
- It keeps Supabase Auth in charge of the session contract
- It avoids introducing a separate server callback layer just to complete PKCE inside an extension

**Alternative considered:** PKCE with a separate callback exchange — rejected because it adds callback/exchange complexity without clear benefit in this MV3 extension architecture.

**Alternative considered:** Keep using `chrome.identity.getAuthToken()` and translate Google tokens into Supabase sessions on the backend — rejected because it is still a hybrid model with a custom token bridge.

### 3. Session lifecycle SHALL be centralized in the extension service worker

**Decision:** The service worker SHALL become the central auth/session broker for the extension. It will persist the Supabase session in `chrome.storage.local`, restore it on startup, refresh it when needed, and expose auth state to the popup.

**Why?** The popup is ephemeral. Session refresh and restoration need one authority to avoid races, repeated refresh attempts, and inconsistent auth state.

**Design notes:**
- Use a single storage key for the current Supabase session
- Gate refresh attempts to avoid concurrent refresh storms
- Treat cached subscription state as UI state, not as the source of truth for auth
- Never log the callback URL or tokens returned from the auth redirect

### 4. `auth.users.id` SHALL become the canonical user key for app data

**Decision:** The final model SHALL key user-scoped app data from `auth.users.id`. `user_profiles` will either be keyed directly by `auth.users.id` again or carry a required unique FK to it during migration, with the end state aligned to authenticated users rather than a parallel identity table.

**Why?** This restores the original model the schema was built for and removes the need for custom user identity keys such as `google_id`.

**Migration approach:**
- Introduce a temporary mapping from existing `user_profiles` rows to `auth.users`
- Backfill `auth.users` for existing customers
- Backfill subscriptions and other user-scoped rows to the authenticated user key
- Cut over codepaths to the authenticated user key before dropping legacy-only identity fields

### 5. User-facing edge functions SHALL accept Supabase JWTs only

**Decision:** `get-subscription-status`, `create-paddle-checkout`, `check-reminder-limit`, and portal/authenticated account endpoints SHALL require a Supabase JWT in the `Authorization` header and resolve the current user from Supabase Auth.

**Why?** One auth contract is easier to secure, easier to test, and easier to audit.

**Authorization model:**
- Prefer user-scoped access patterns and RLS-compatible queries for authenticated reads
- Use service-role writes only where administrative behavior is required, and only after a verified user identity is established
- Keep service-role-only access for webhooks and backend-only jobs

### 6. Plan state SHALL come only from `subscriptions`

**Decision:** `user_profiles.plan_type` will be removed. The backend SHALL derive plan type and entitlements solely from `subscriptions`.

**Why?** Plan state must live in one table. The `subscriptions` table already models trial, active, grace, cancellation, and billing dates.

### 7. Reminder-limit fallback SHALL be conservative when the backend is unavailable

**Decision:** Reminder creation will call the backend before persistence. When the backend is unreachable, the extension SHALL apply a conservative fallback rather than granting premium-only behavior from unverifiable local state.

**Why?** A local premium fallback reintroduces the same bypass problem this change is intended to remove.

**Fallback rule:**
- Never grant premium unlimited reminders from stale local state alone
- If a fallback is needed, cap behavior to the free-tier limit unless the backend has recently verified premium entitlement

### 8. Paddle integration SHALL use the authenticated Supabase user

**Decision:** Checkout and subscription lifecycle flows SHALL use the authenticated Supabase user ID (`auth.users.id`) as the stable customer linkage in backend logic and Paddle `custom_data`.

**Why?** This removes email-based and custom-profile-based user identification from payment flows.

## Risks / Trade-offs

- **[Migration complexity]** Existing records are keyed to legacy `user_profiles.id`, not `auth.users.id`. Mitigation: use a staged migration with temporary mapping columns and backfill before enforcing the final schema.
- **[Extension auth rewrite]** This is a real client auth rewrite, not an endpoint swap. Mitigation: centralize auth work in the service worker and keep popup changes thin.
- **[Session handling in MV3]** Popup and service worker lifecycles are different from a normal browser SPA. Mitigation: make the service worker the only session authority and persist session state explicitly.
- **[OAuth redirect handling]** Chrome extension redirect plumbing is more specialized than a web app. Mitigation: pin one supported OAuth flow and test it end to end before migrating premium logic.
- **[Reminder count still client-reported]** Backend still cannot fully verify local reminder count until reminders are stored server-side. Mitigation: keep backend plan authority and conservative fallback behavior; server-side reminders remain a future enhancement.

## Migration Plan

1. **Configure Supabase Auth** — Enable Google provider, register Chrome extension redirect URL, define session storage contract
2. **Introduce temporary identity mapping** — Add migration-safe mapping from legacy profile records to `auth.users`
3. **Backfill authenticated users** — Create/link `auth.users` records for existing customers and associate subscriptions
4. **Cut user-facing backend to JWT auth** — Update all extension-facing edge functions to require Supabase JWTs
5. **Implement extension session management** — Replace Chrome Identity token retrieval with Supabase sign-in, restore, refresh, and sign-out flows
6. **Cut popup and premium refresh flows** — Rebase popup state on Supabase session + subscription refresh
7. **Remove legacy custom-auth paths** — Delete Google-token validation paths and dead hybrid auth logic
8. **Validate end-to-end** — Run Playwright coverage for sign-in, session restore/refresh, premium state, and checkout/subscription flows

## Open Questions

- Should `user_profiles` survive as a thin app-profile table, or should app-specific user metadata move into `auth.users` metadata where practical?
- How strict should reminder creation be during backend outages: free-tier fallback only, or hard-fail until the backend can verify entitlement?
